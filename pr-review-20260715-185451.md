## PR #2869 — "Improve Add Token disclosure for SAC"

**Verdict: Approve with minor follow-ups.** This is a large, careful change and
— importantly — the author has already resolved the serious concerns raised in
the earlier review rounds (verified-list SAC skip, orphaned add/remove-asset
metrics, the Done-click race, the SEP-41 storage-failure regression, the dead
`ADD_TOKEN_FAILURE`/`apiError` plumbing, and the fee-unit mismatch). What
remains is edge-case / cosmetic. See "Already addressed" below for the
verification, then the ranked findings.

### PR-specific invariant (inferred — stated as an assumption)

> Once a SAC/classic trustline actually succeeds on-chain, the dApp's
> `addToken()` must resolve as **success** (`{ contractId }`), never as "user
> rejected"; conversely a SEP-41 add must report success to the dApp **only if**
> the token was actually persisted — and the SAC-vs-SEP-41 classification must
> route each token down the correct flow (2-step review vs. 1-step approval).

**Standing (secrets) invariant:** PASS. The diff touches trustline building,
token-id storage, and dApp messaging only. No mnemonic/seed/private-key/password
material is written, logged (`console.error`/`captureException` carry storage
errors and `JSON.stringify(tokenDetails)`, not keys), or placed in any
request/response payload.

### Already addressed (verified in current head — not findings)

- **Verified-list path no longer silently skips the trustline.**
  `useTokenLookup.ts` now runs the authoritative `isSacContractExecutable` on
  the verified-list branch when list-derived `isAssetSac` says "not a SAC," and
  falls back to the manual (contract-derived) lookup
  (`useTokenLookup.ts:163-185`).
- **Add/remove-asset metrics re-wired.** `SubmitTx/index.tsx` re-emits
  `manageAssetAddAsset`/`manageAssetRemoveAsset` on tx success (the emitters
  that `useChangeTrustline` used to own before it was deleted).
- **Done-click race fixed.** `onTransactionSuccess` kicks off
  `addTokenAndClose(true)` and stores the promise; `handleTrustlineDone` awaits
  it before `window.close()` (`AddToken/index.tsx:180-192`) — so
  `response(true)` beats `rejectOnWindowClose`.
- **SEP-41 storage-failure regression fixed.** `handlers/addToken.ts:70` gates
  the swallow on `isTrustlineBacked`, so a SEP-41 persist failure surfaces
  `response(false)` again.
- **Dead failure plumbing removed.** `AddTokenResponse` is back to `boolean`; no
  `ADD_TOKEN_FAILURE` enum / `AddTokenFailureMessage` / `apiError` variant
  ships.
- **Fee units consistent.** `getManageAssetXDR` expects XLM
  (`xlmToStroop(recommendedFee)`); the editable `fee` state, `initialFee`, and
  `useGetChangeTrust({ recommendedFee: fee })` are all XLM.

### Findings (ranked by severity)

**1. [correctness] A SEP-41 internal storage failure is reported to the dApp as
"user rejected," not as an error.**
`extension/src/background/messageListener/handlers/addToken.ts:70-76` →
`extension/src/background/messageListener/freighterApiMessageListener.ts:323-333`

Scenario: a dApp requests a SEP-41 token; `localStore.setItem` throws (quota
exceeded / corrupt store). `addTokenWithContractId` returns
`{ error: "Failed to add token" }`, the handler computes `hasError = true` and
calls `tokenResponse.response(false)`, which the listener maps to
`FreighterApiDeclinedError` (code -4, "The user rejected this request"). The
dApp is told the user declined when in fact an internal write failed and the
user approved. The earlier iteration's `ADD_TOKEN_FAILURE`/`apiError` path was
meant to distinguish these but was removed, so the two outcomes are now
indistinguishable to the dApp. Narrow (only on a thrown `setItem`) and closer to
an _incomplete improvement_ than a regression — but worth a one-line note in the
PR that "internal failure surfaces as declined for now" so it's a conscious
call.

**2. [toctou] Residual: a total ADD_TOKEN round-trip failure after an on-chain
success still reports "rejected."**
`extension/src/popup/views/AddToken/index.tsx:190-192`

`handleTrustlineDone` does
`await (addTokenPromiseRef.current ?? addTokenAndClose(true))` and then
**unconditionally** `window.close()`. `isTrustlineBacked=true` guarantees the
background answers `response(true)` even when _storage_ fails — but if the
messaging round-trip itself fails (the thunk rejects / `sendMessageToBackground`
throws), `addTokenAndClose(true)` resolves `false`, `response()` is never
delivered, and the subsequent `window.close()` lets `rejectOnWindowClose` win →
the dApp hears `FreighterApiDeclinedError` for a trustline that already
succeeded on-chain — exactly the invariant the fix targets. Far narrower than
the original race (needs a messaging failure, not just a fast click), so low
priority; the clean fix is to resolve the window-close fallback as success once
a trustline submit has succeeded, rather than relying on the response callback
winning the race.

**3. [scope] `AutoLockTimer` change is unrelated to the Add Token SAC feature.**
`extension/src/popup/views/AutoLockTimer/index.tsx:95,107`

Retitling "Auto-Lock Timer" → "Auto-lock timer" and reformatting the
`saveSettings` args are a drive-by with no connection to SAC disclosure.
Harmless, but a split candidate — it widens the diff and the blast radius of a
revert. (The PR description already acknowledges bundling some unrelated UI
tidy-ups.)

**4. [duplication] The SAC e2e stub injection is copy-pasted verbatim across
three tests.**
`extension/e2e-tests/integration-tests/freighterApiIntegration.test.ts:905, 1026, 1280`
(plus the `chrome.runtime.sendMessage` delay patch at `:1074`)

The ~40-line
`context.addInitScript(() => { window.fetch = … is-sac-contract / token-details / asset-list … })`
block is duplicated three times (the third copy additionally stubs
`asset-list`). This is duplication the diff itself introduces, so "out of scope"
doesn't apply — extract a `stubSacViaInitScript(context, { withAssetList })` and
`delayAddTokenRoundTrip(context)` into `e2e-tests/helpers/stubs.ts` (next to the
already-added `stubIsSacTrue`/`stubSacTokenDetails`). Any future change to the
fetch-override shape currently has to be made in three places.

**5. [i18n] The submit-error body text is hardcoded English and untranslated.**
`extension/src/popup/helpers/useSetupAddTokenFlow.ts:70,96`;
`extension/src/popup/locales/pt/translation.json:213,491`

`"Failed to add token. Please retry or cancel."` is set directly on
`submitError` (both the `getThunkErrorMessage` default and the `catch`) without
`t()` and it isn't in `translation.json`, while the surrounding Notification
_title_ is translated (`t("Failed to add token.")`, `AddToken/index.tsx:640`).
Result: a translated title over an English body. Separately, the pt locale ships
`"Retry": "Retry"` and `"Failed to add token.": "Failed to add token."` as
English placeholders even though sibling new strings (e.g.
`"It cannot be added again."`) were translated. Minor, but the error path is
exactly where non-English users are worst served.

**6. [efficiency] SAC review re-fetches data the Add Token screen already had
(corroborates prior review; still open).**
`extension/src/popup/components/manageAssets/ManageAssetRows/ChangeTrustInternal/index.tsx:98`

`ChangeTrustInternal` calls `useNetworkFees()` again (a second `feeStats()`
round-trip — only `initialFee` is threaded from the parent, not
`recommendedFee`), and `useChangeTrustData` re-runs `scanAsset` for the same
`${code}-${issuer}` the Add Token screen already scanned (not threaded down).
Not user-visible beyond latency/requests. Note also that `fetchData` is now
`useCallback`-memoized with `networkDetails` in its dep array and the effect is
`[fetchData]`; this is correct **only while the `networkDetails` prop is
referentially stable** — if a parent ever passes a freshly-constructed
`networkDetails` each render, the memo breaks and `fetchData` re-fires on every
render. Worth a quick confirmation that the `useGetAppData`/redux source is
stable (current tests pass, so it appears to be).

  rather than blocking a legitimate add.
  `getAccountBalances(publicKey, networkDetails, isMainnet, shouldSkipScan)` is
  called with the correct 4-arg signature.

  (`isTrustlineBacked:true` → `response(true)`) vs SEP-41 (`response(false)`) vs

  deterministically by delaying the round-trip 1s and clicking Done on the same
  tick; `AddToken.test.tsx` pins "Done doesn't double-dispatch." These would go
  red if the respective behaviors regressed.
